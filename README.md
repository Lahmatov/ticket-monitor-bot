# Ticket monitor → Telegram

Следит за билетными сайтами — сборная Португалии
<https://bilheteira.fpf.pt/>, **Sporting CP** <https://tickets.sporting.pt/pt>,
**SL Benfica** <https://www.slbenfica.pt/pt-pt/bilhetes> и **FC Porto**
<https://bilhetes.fcporto.pt/> (везде только основная мужская футбольная
команда) — и присылает уведомление в Telegram (на английском), как только
матч появляется в продаже. Источники задаются в `sources.json` — добавить ещё
сайт можно, не трогая код (см. «Источники» ниже).

Работает внутри **GitHub Actions**: одна задача живёт ~5,5 часа и сама
проверяет сайты по расписанию ниже, а в конце запускает следующую такую же
задачу — получается непрерывная цепочка. Уже сыгранные матчи (начались более
3 часов назад) в отчёт не попадают.

## Что присылает

**Алерт о продаже** приходит, когда подходящий матч переходит в статус
**«в продаже»** (`AVAILABLE`). «Подходящий» = проходит фильтр источника (для
FPF — все матчи сборной по слову `portugal`; для Sporting — только основной
мужской футбол). Повторно про тот же матч не пишет (дедуп по `id:URL`).

**Сообщения только при изменениях** (`REPORT_MODE: "changes"` в workflow,
по умолчанию). Бот проверяет сайты по расписанию ниже, но пишет, только если
что-то поменялось: 🎫 алерт «Tickets on sale!» при открытии продаж и
🔔 «Changes» — новый матч или смена статуса (распродано, перепродажа, скоро…),
сгруппировано по командам, со ссылками. Полную сводку (итоги 🟢/🟠/🟡/🔴 и блок
на каждую команду) можно получить в любой момент командой **`/status`**.
`REPORT_MODE: "every"` — старый режим: сводка после каждой проверки.

## Расписание (частота проверки)

Интервал между проверками задаёт сам скрипт в таймзоне `Europe/Lisbon`
(корректно при переходе на летнее/зимнее время), а не cron: на практике GitHub
запускает задачи по cron лишь раз в 2–5 часов. Поэтому задача крутится в цикле
(`--loop-minutes 330`), а cron (`17 */3 * * *`) — только страховка, если
цепочка вдруг прервётся:

| Время в Лиссабоне | Частота проверки |
|-------------------|------------------|
| 07:00–00:00 (день) | случайно каждые 20–40 минут |
| 00:00–07:00 (ночь) | случайно каждые 100–140 минут |

Интервал после каждой проверки выбирается случайно (чтобы запросы не шли
«как по часам»). Поменять диапазоны — константы `DAY_INTERVAL_RANGE_MIN` /
`NIGHT_INTERVAL_RANGE_MIN`
в начале `monitor.py`.

**Остановить бота:** Actions → Ticket monitor → `…` → *Disable workflow*
(или отменить текущий запуск — отменённый запуск следующий не стартует).
**Запустить снова:** *Enable workflow* и *Run workflow* в режиме `normal`.

> **Про минуты GitHub Actions.** Задача работает почти круглосуточно, поэтому
> репозиторий должен быть **публичным** — там минуты безлимитны. На приватном
> бесплатного лимита (2000 мин/мес) не хватит.

## Настройка (один раз)

1. **Секреты репозитория.** Settings → Secrets and variables → Actions →
   *New repository secret*:
   - `TELEGRAM_BOT_TOKEN` — токен бота от [@BotFather](https://t.me/BotFather).
   - `TELEGRAM_CHAT_ID` — куда слать (см. ниже).

2. **Как узнать `TELEGRAM_CHAT_ID`** (любой из способов):
   - **Через бота (проще всего):** напиши боту в Telegram любое
     сообщение, затем Actions → *Run workflow* → режим **`chatid`** — id
     появится прямо в логе. (Достаточно, чтобы был задан секрет
     `TELEGRAM_BOT_TOKEN`.)
   - **Через браузер (работает сразу):** напиши боту сообщение, открой
     `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найди в JSON
     `"chat":{"id":<число>...}`. Для личных сообщений — положительное число,
     для группы — со знаком минус.

   **Доступ для других людей (по запросу).** Человек пишет боту `/start` —
   бот отвечает ему, что запрос отправлен, а тебе (первый id в
   `TELEGRAM_CHAT_ID`) приходит сообщение с кнопками **✅ Allow / ❌ Deny**.
   После Allow человек получает те же сводки и алерты; `/stop` — отписаться.
   Твои команды боту: `/list` — кто получает сообщения (с кнопками «Remove»).
   Бот читает входящие раз в минуту (пока работает цикл). Одобренные хранятся
   в `state.json` (кэш Actions). Технические алерты об ошибках идут только тебе.
   Можно и вручную: перечислить id через запятую в `TELEGRAM_CHAT_ID`.

3. **Активация.** Код уже в ветке по умолчанию (`main`), поэтому расписание
   активно сразу после первого пуша. Вкладку **Actions**, возможно, придётся
   один раз включить кнопкой «I understand my workflows, go ahead and enable them».

## Проверка после настройки

Вкладка **Actions → Ticket monitor → Run workflow**, выбери режим:

- **`chatid`** — печатает в лог chat id из последних сообщений боту (см. шаг 2).
- **`test`** — бот шлёт тестовое сообщение в Telegram (проверка токена и chat id).
- **`diagnostic`** — загружает страницу, печатает в лог всё, что распарсил
  (список событий, их статусы, какие совпали по ключевому слову), и прикладывает
  сырой HTML артефактом `fpf-page-html`. **Уведомления не шлёт.**
- **`normal`** — обычный запуск.

Начни с `diagnostic`: по логу видно, правильно ли определяются матчи и статусы.

## Если парсер не видит матчи / путает статусы

Отсюда (из среды разработки) сайты недоступны, поэтому парсер написан
эвристически: он ищет ссылки на страницы событий и определяет статус по словам
рядом (`comprar`, `esgotado`, `brevemente`…). Если реальная вёрстка отличается,
подстрой источник **без правки кода** — добавь селекторы прямо в `sources.json`:

| Поле в `sources.json` | Значение |
|-----------------------|----------|
| `keywords` | ключевые слова (список); `[]` = все события |
| `exclude_keywords` | слова-исключения: событие с таким словом отсеивается |
| `event_selector` | CSS-селектор карточки события (точный режим) |
| `title_selector` | CSS-селектор заголовка внутри карточки |
| `link_selector` | CSS-селектор ссылки «купить» внутри карточки |
| `url` | адрес страницы со списком |

Точные селекторы бери из HTML, который выгрузил режим `diagnostic` (артефакт
`diagnostic-html`). Слова для статусов (`SOLD_OUT_WORDS`, `SOON_WORDS`,
`BUY_WORDS`) при необходимости правятся в начале `monitor.py`.

> Есть и «legacy»-режим одного источника через переменные окружения
> `FPF_URL` / `MATCH_KEYWORDS` / `EVENT_SELECTOR` … — если они заданы, они
> переопределяют `sources.json`. Для нескольких сайтов используй `sources.json`.

## Источники (несколько сайтов)

Список сайтов — в `sources.json`. Каждый источник:

У каждого источника свой способ получения данных (`api_type`):

| `api_type` | как работает | кто использует |
|------------|--------------|----------------|
| `json` | GET `api_url` → JSON, разбирает `parser` или общий разбор | **FPF**, **Sporting** |
| `browser` | рендер `browse_url` в headless-Chromium, парс DOM | — (поддерживается, но сейчас не нужен; требует `playwright`) |
| `html` | обычный GET + эвристический парс HTML | — (по умолчанию) |

Все сайты читаются без браузера:
- **FPF** — новый сайт (с 10.2026): OData
  `https://score2-external-api.fpf.pt/api/ticketing-fo/odata/Events`,
  `parser: "fpf_odata"`: только основная мужская сборная (теги `SUB21`,
  `FEM`, `FUTSAL`… и турниры «S21»/«Sub-…» отсеиваются); статус из `IsSoldOut`
  и окна продаж `SaleStartDate`/`SaleEndDate`.
- **Sporting** — `https://tickets.sporting.pt/api/match/allopengames`,
  `parser: "sporting_api"`: все открытые игры, только `modality = Futebol`;
  статус из `soldOut` / `allowSale` **и** `disabledReasonDesc` (надпись на
  неактивной кнопке «Brevemente disponível», «Esgotado»).
- **Benfica** — HTML `https://www.slbenfica.pt/pt-pt/bilhetes`,
  `parser: "benfica"`: только вкладка «Equipa A»; статус из плашки карточки
  (Esgotado → распродано, Mercado Secundário → 🟠 только перепродажа,
  Por iniciar → скоро, Exclusivo a … → в продаже с пометкой). Год на сайте не
  указан — берётся ближайший к сегодняшней дате.
- **FC Porto** — GraphQL `https://bilhetes-api.fcporto.pt/api/graphql`
  (тот же запрос `matchesByDate`, что делает сайт), `parser: "fcporto"`:
  только матчи, где одна из команд ровно «FC Porto»; статус из поля `status`
  (неизвестные значения показываются как есть).

Ссылки ведут сразу в покупку конкретного матча: Sporting —
`tickets.sporting.pt/pt/evento/<token>`, Benfica — ссылка «Bilhetes» с карточки,
Porto — `bilhetes.fcporto.pt/jogos/<id>/comprar`, FPF —
`bilheteira.fpf.pt/checkout/<Code>`.
В сводке название матча — кликабельная ссылка.

Статус Sporting берётся со страницы самого матча
(`/api/match/opengames?gamecode=<token>` — то же, что загружает сайт при
открытии матча): надпись `disabledReasonDesc` в общем списке оказалась
ненадёжной («Brevemente disponível» у матча, на который билеты уже продавались).

Уже сыгранные матчи (начались > 3 ч назад) скрываются. Если матч перестал быть
доступен (распродан/закрыт), бот его «забывает» — при возврате билетов придёт
новый алерт.

Разведка нового сайта: workflow **Explore ticket site (one-off)** открывает
страницу в Chromium и печатает в лог все JSON/API-запросы, которые она делает.

Общие поля:

- `id` — короткий идентификатор (в дедупликации; не меняй после запуска).
- `keywords` — событие подходит, если название содержит **любое** из слов.
  Пустой `[]` = все события источника.
- `exclude_keywords` — событие **отсеивается**, если содержит любое из слов
  (страховка: женская команда, молодёжка и т.п.).
- для `json`: `api_url` (+ опц. `parser`).
- для `browser`: `browse_url`, `wait_ms`, `parser` (нужен пакет `playwright`).
- для `html`: `event_selector` / `title_selector` / `link_selector`.

Правило отбора: уведомляем, если **не** попало под `exclude_keywords` **и**
(`keywords` пуст **или** название содержит одно из `keywords`). Дедупликация у
каждого источника своя, сбой одного не мешает остальным; уведомления идут в один
чат с пометкой источника.

## Локальный запуск

```bash
pip install -r requirements.txt

# посмотреть, что видит парсер (нужен доступ к сайтам из твоей сети):
python monitor.py --mode diagnostic

# тестовое сообщение в Telegram:
TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=... python monitor.py --mode test
```

## Состояние

Между запусками список уже отправленных матчей хранится в кэше Actions
(`state.json`), чтобы не слать дубли и не засорять историю `main` коммитами.
Матч, пропавший из списка более чем на `FORGET_AFTER_DAYS` (7) дней, забывается —
если продажи откроют заново, придёт новое уведомление.
