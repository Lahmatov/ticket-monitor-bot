# Ticket monitor → Telegram

Следит за билетными сайтами (по умолчанию — сборная Португалии
<https://bilheteira.fpf.pt/> и **Sporting CP**
<https://www.sporting.pt/>) и присылает уведомление в Telegram, как только
матч появляется в продаже. Источники задаются в `sources.json` — добавить ещё
сайт можно, не трогая код (см. «Источники» ниже).

Работает не как постоянный бот, а как короткая задача в **GitHub Actions**:
по расписанию скрипт один раз загружает страницу, сравнивает с сохранённым
состоянием, шлёт уведомление о новом матче в продаже и завершается.

## Что присылает

Уведомление приходит, когда подходящий матч переходит в статус **«в продаже»**
(`AVAILABLE`). «Подходящий» = проходит фильтр источника (для
FPF — все матчи сборной по слову `portugal`; для Sporting — только основной
мужской футбол: прочие виды спорта, женская команда и молодёжка отсеиваются
через `exclude_keywords`). Про статусы «esgotado»
(распродано) и «brevemente» (скоро) уведомлений нет. Повторно про тот же матч
не пишет (дедупликация по `id:URL` события).

## Расписание (частота проверки)

Гейтинг по времени делает сам скрипт в таймзоне `Europe/Lisbon` — корректно и
при переходе на летнее/зимнее время:

| Время в Лиссабоне | Частота проверки |
|-------------------|------------------|
| 07:00–00:00 (день) | каждые ~20 минут |
| 00:00–07:00 (ночь) | примерно раз в 2 часа |

Хочешь чаще/реже днём — поменяй `cron` в
`.github/workflows/monitor.yml`:

- каждые 15 мин: `"*/15 6-23 * * *"`
- каждые 30 мин: `"0,30 6-23 * * *"`

> **Про минуты GitHub Actions.** На **публичном** репозитории минуты
> бесплатны и безлимитны. На **приватном** есть месячный лимит (обычно 2000
> мин). Текущая настройка (~20 мин днём + ~2 ч ночью) — это ~55 коротких
> запусков в сутки (~1 мин каждый), т.е. ~1600 мин/мес — вписывается. Если
> поставишь 15 мин днём, будет ~70/сутки (~2100 мин/мес) — уже впритык к лимиту.

## Настройка (один раз)

1. **Секреты репозитория.** Settings → Secrets and variables → Actions →
   *New repository secret*:
   - `TELEGRAM_BOT_TOKEN` — токен бота от [@BotFather](https://t.me/BotFather).
   - `TELEGRAM_CHAT_ID` — куда слать (см. ниже).

2. **Как узнать `TELEGRAM_CHAT_ID`** (любой из способов):
   - **Через бота (проще всего):** напиши боту в Telegram любое
     сообщение, затем Actions → *Run workflow* → режим **`chatid`** — id
     появится прямо в логе. (Достаточно, чтобы был задан секрет
     `TELEGRAM_BOT_TOKEN`.)
   - **Через браузер (работает сразу):** напиши боту сообщение, открой
     `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найди в JSON
     `"chat":{"id":<число>...}`. Для личных сообщений — положительное число,
     для группы — со знаком минус.

3. **Активация.** Код уже в ветке по умолчанию (`main`), поэтому расписание
   активно сразу после первого пуша. Вкладку **Actions**, возможно, придётся
   один раз включить кнопкой «I understand my workflows, go ahead and enable them».

## Проверка после настройки

Вкладка **Actions → Ticket monitor → Run workflow**, выбери режим:

- **`chatid`** — печатает в лог chat id из последних сообщений боту (см. шаг 2).
- **`test`** — бот шлёт тестовое сообщение в Telegram (проверка токена и chat id).
- **`diagnostic`** — загружает страницу, печатает в лог всё, что распарсил
  (список событий, их статусы, какие совпали по ключевому слову), и прикладывает
  сырой HTML артефактом `fpf-page-html`. **Уведомления не шлёт.**
- **`normal`** — обычный запуск.

Начни с `diagnostic`: по логу видно, правильно ли определяются матчи и статусы.

## Если парсер не видит матчи / путает статусы

Отсюда (из среды разработки) сайты недоступны, поэтому парсер написан
эвристически: он ищет ссылки на страницы событий и определяет статус по словам
рядом (`comprar`, `esgotado`, `brevemente`…). Если реальная вёрстка отличается,
подстрой источник **без правки кода** — добавь селекторы прямо в `sources.json`:

| Поле в `sources.json` | Значение |
|-----------------------|----------|
| `keywords` | ключевые слова (список); `[]` = все события |
| `exclude_keywords` | слова-исключения: событие с таким словом отсеивается |
| `event_selector` | CSS-селектор карточки события (точный режим) |
| `title_selector` | CSS-селектор заголовка внутри карточки |
| `link_selector` | CSS-селектор ссылки «купить» внутри карточки |
| `url` | адрес страницы со списком |

Точные селекторы бери из HTML, который выгрузил режим `diagnostic` (артефакт
`diagnostic-html`). Слова для статусов (`SOLD_OUT_WORDS`, `SOON_WORDS`,
`BUY_WORDS`) при необходимости правятся в начале `monitor.py`.

> Есть и «legacy»-режим одного источника через переменные окружения
> `FPF_URL` / `MATCH_KEYWORDS` / `EVENT_SELECTOR` … — если они заданы, они
> переопределяют `sources.json`. Для нескольких сайтов используй `sources.json`.

## Источники (несколько сайтов)

Список сайтов — в `sources.json`. Каждый источник:

```json
{
  "id": "sporting",
  "name": "Sporting CP",
  "url": "https://tickets.sporting.pt/pt",
  "keywords": [],
  "event_selector": "",
  "title_selector": "",
  "link_selector": ""
}
```

- `id` — короткий идентификатор (используется в дедупликации, не меняй после запуска).
- `keywords` — фильтр по названию: событие подходит, если содержит **любое** из
  слов. **Пустой список `[]` = следить за всеми событиями** на этом сайте.
- `exclude_keywords` — событие **отсеивается**, если содержит любое из этих слов
  (сильнее `keywords`). Так у Спортинга отсекаются футзал, гандбол, женская
  команда, молодёжка/юниоры и т.п. — остаётся только основной мужской футбол.
- `event_selector` / `title_selector` / `link_selector` — необязательные CSS-селекторы
  (точный режим). Пусто → эвристика.

Правило отбора: событие уведомляется, если **не** попало под `exclude_keywords`
**и** (список `keywords` пуст **или** название содержит одно из `keywords`).

Дедупликация у каждого источника своя (ключ `id:URL`), сбой одного источника не
мешает остальным. Уведомления идут в один и тот же чат, с пометкой, какой это
сайт.

> **Про Sporting.** Источник смотрит `https://tickets.sporting.pt/pt`. Сайт
> билетной платформы может подгружать список матчей через JavaScript — тогда
> обычный парсер увидит пустую страницу. Это сразу покажет прогон `diagnostic`
> (сколько событий распозналось для `sporting`). Если так — напиши мне,
> переключу этот источник на его внутренний JSON-API или на headless-браузер.

## Локальный запуск

```bash
pip install -r requirements.txt

# посмотреть, что видит парсер (нужен доступ к сайту из твоей сети):
python monitor.py --mode diagnostic

# тестовое сообщение в Telegram:
TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=... python monitor.py --mode test
```

## Состояние

Между запусками список уже отправленных матчей хранится в кэше Actions
(`state.json`), чтобы не слать дубли и не засорять историю `main` коммитами.
Матч, пропавший из списка более чем на `FORGET_AFTER_DAYS` (7) дней, забывается —
если продажи откроют заново, придёт новое уведомление.
